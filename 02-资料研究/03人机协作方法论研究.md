# 03 人机协作方法论研究

更新时间：2026-07-27

## 研究目的

为 `A-24—A-30` 提供跨 Agent 工具的方法论依据。课件不讲某个产品的按钮和操作步骤，只提炼可迁移的任务分层、工具调度、展示载体、快速原型和上下文管理原则。

## 主要结论

1. **Agent 的价值不在于亲自完成每一种底层操作，而在于理解目标、组织步骤、选择工具并根据结果继续推进。** 对计算、转换、可视化等确定性工作，应优先调度脚本和专业工具。
2. **交付格式与中间工作格式可以分开。** Office 文件适合正式交付；Markdown、CSV、JSON 和代码更适合结构清楚、可比较、可自动处理的中间协作层。但不能将 DOCX、XLSX 或 PPTX 的速度与 Token 成本写成不受具体产品解析流程影响的绝对结论。
3. **汇报的核心是信息表达，不是固定文件格式。** PPT 适合线性讲述和正式分发；HTML/CSS/JavaScript 与 ECharts 等前端技术适合更自由的布局、交互图形、实时数据与代码动画。
4. **生成式能力适合快速扩大设计探索空间。** 原型用于让想法可见并降低沟通成本；品牌规范、工程实现、版权、安全和最终质量仍需要专业人员负责。
5. **长期工作依赖外化状态。** 长会话会积累大量中间信息，部分工具会在上下文较长时进行摘要压缩；孤立的新会话又没有历史。项目说明、当前进展、决策记录、任务交接和版本历史共同构成可持续的组织记忆。

## 表述边界

- 不写“Agent 不能处理 Word、Excel、PPT”，统一表述为“可以处理，但不一定是效率、稳定性或可控性最优的中间工作层”。
- 不写“DOCX 一定更费 Token”，统一表述为“复杂格式通常需要额外解析，实际效率取决于具体工具的处理方式”。
- 不写“大模型不会计算”，统一表述为“对需要精确、可重复和可复核的计算，应调度脚本或专业工具执行”。
- 不写“长会话一定让模型变笨”，统一表述为“有效信息可能受到噪声、信息位置和摘要压缩影响”。
- 快速原型不用于贬低设计师或工程师，而用于验证方向、减少抽象沟通，并把专业团队的时间投入到完善与兜底。

## 主要来源

- OpenAI, *Run long horizon tasks with Codex*：长期任务采用计划、工具调用、观察、修正和更新项目状态的循环；项目文件是持久状态的一部分。https://developers.openai.com/blog/run-long-horizon-tasks-with-codex
- OpenAI, *Codex best practices*：任务应明确目标、上下文、约束和完成标准；复杂工作适合先规划并保持边界清楚。https://developers.openai.com/codex/learn/best-practices
- OpenAI, *AGENTS.md*：仓库级说明文件可保存项目结构、约定、验证方式和持续指导。https://developers.openai.com/codex/agent-configuration/agents-md
- Anthropic, *Claude Code memory*：新会话需要通过项目级记忆文件获得持久指导。https://docs.anthropic.com/en/docs/claude-code/memory
- Anthropic, *Manage costs effectively*：上下文会随会话增长，压缩机制会对较早内容进行摘要。https://code.claude.com/docs/en/costs
- Liu et al., *Lost in the Middle*：长上下文模型对信息的利用会受到信息位置影响，不能只以“上下文窗口放得下”推断所有信息都能同等有效使用。https://arxiv.org/abs/2307.03172
- Apache ECharts, *Dataset*：结构化数据可通过 dataset 统一管理并映射到多种图表。https://echarts.apache.org/handbook/en/concepts/dataset/
- WorkBuddy, *Project*：产品级项目可让多个任务共享指令、资源和能力；该资料只作为“项目化协作”的一个实现例证，不作为本章产品操作说明。https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Project
